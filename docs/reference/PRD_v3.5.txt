1 Gambaran produk
1.1 Masalah dan hasil yang diharapkan
Pendaftaran, iuran, informasi organisasi, kegiatan, dan komunikasi alumni perlu terhubung pada satu identitas
keanggotaan. Anggota harus dapat mengetahui status pembayaran dan masa aktif KTA. Pengurus harus dapat
memproses antrean, mengendalikan akses, dan menelusuri keputusan tanpa mengandalkan pesan pribadi.
KAPDH Apps dibangun dari awal. Backend, database, dan hosting web berjalan di VPS yang dikelola melalui
Coolify sejak rilis pertama. Tidak ada data, akun, transaksi, atau aplikasi klien sebelumnya yang harus
dipindahkan atau dijaga kompatibilitasnya. Jumlah pengguna awal belum diketahui; kapasitas dan target diukur
melalui uji beban (N-04) dan baseline 30 hari setelah go-live.
1.2 Tujuan produk
Menghasilkan alur daftar, verifikasi email, pembayaran, persetujuan, dan penerbitan KTA yang dapat
ditelusuri.
Menegakkan masa aktif keanggotaan serta akses terbatas setelah kedaluwarsa atau suspend.
Menyatukan berita, kegiatan, tiket, direktori, chat, dan notifikasi dengan identitas anggota.
Memberikan pengurus portal operasional dengan izin per tindakan, MFA, dan audit.
Menjalankan layanan inti pada VPS sendiri serta memulihkan layanan dari backup di luar VPS.
Tidak mengumpulkan NIK, membatasi paparan data profil, dan menyediakan penghapusan akun.
1.3 Ketentuan pemilik dan batas produk
Backend menggunakan VPS dan PostgreSQL sendiri. Supabase, Vercel, maupun backend-as-a-service lain tidak
dipakai sebagai database, autentikasi, hosting, atau ketergantungan runtime. Berkas menggunakan disk VPS
terlebih dahulu dengan antarmuka StorageDriver untuk perpindahan ke S3-compatible. Aplikasi anggota hanya
Flutter Android dan iOS; tidak ada aplikasi anggota berbasis web. Pengurus menggunakan web admin React.
Deploy dan operasi menggunakan Coolify.
Ketentuan tanpa BaaS tidak menghilangkan layanan email, FCM, APNs, DNS, sertifikat TLS, maupun tujuan
backup di luar VPS. Layanan tersebut tetap tercatat sebagai dependensi operasional. Firebase dipakai untuk
push, bukan sebagai database atau autentikasi anggota.
Di luar R1.0: aplikasi anggota berbasis web atau PWA, migrasi atau impor massal data dari sistem lain, multi-
organisasi, marketplace, dompet saldo, pembayaran berulang otomatis, payment gateway otomatis, panggilan
suara/video, chat terenkripsi end-to-end, check-in offline, serta fitur AI. Refund pada R1.0 ditangani sebagai
proses administratif tercatat; integrasi pengembalian dana otomatis tidak termasuk.

2 Persyaratan umum
2.1 Sumber kebenaran dan waktu
API menjadi pintu akses seluruh klien. UI boleh membantu validasi dan routing, tetapi server selalu memeriksa
identitas, izin, status keanggotaan, kepemilikan objek, serta keadaan terbaru. Constraint dan transaksi database
menjaga nomor unik, uang, kuota, serta keputusan tunggal.
Timestamp disimpan dalam UTC menggunakan timestamptz. Pengguna melihat tanggal dalam Asia/Jakarta
kecuali event menetapkan zona waktu lain. Periode 12 bulan menggunakan penambahan bulan kalender dari
waktu aktivasi, bukan 365 hari. Keanggotaan berakhir saat now >= expires_at. Pada tanggal yang tidak tersedia
di bulan tujuan, gunakan hari terakhir bulan tersebut dengan jam yang sama. Aturan tanggal diuji, termasuk 29
Februari.
2.2 Matriks akses berdasarkan status
Status akun users membatasi autentikasi. Status masa keanggotaan dihitung dari waktu berlaku. Suspend
adalah lapisan moderasi yang mengalahkan masa aktif. Persetujuan pembayaran tidak pernah menghapus
suspend. Hasil effective_status memakai label unverified, verified, expiring, expired, dan suspended sebagai
kontrak bagi seluruh klien.

2.5 Baseline autentikasi dan unggahan
Sandi wajib berisi 8 sampai 72 byte UTF-8 dengan huruf besar, kecil, angka, dan simbol (disahkan v3.2). Batas
72 byte mengikuti batas input bcrypt. UI menampilkan batas byte dengan jelas (bukan jumlah karakter) dan
server menolak, bukan memotong, input yang melampaui batas. Sandi di-hash dengan bcrypt memakai cost
yang dikalibrasi terhadap VPS. Tidak ada OTP, sandi atau secret TOTP pada log.
OTP berisi 6 digit, berlaku 10 menit, maksimal 5 percobaan, dan kirim ulang paling cepat 60 detik. Pengiriman
ulang membatalkan kode sebelumnya untuk tujuan yang sama. Kode disimpan sebagai hash/HMAC dengan
secret server agar pencarian offline atas ruang 6 digit tidak mudah dilakukan. Challenge terikat akun, tujuan, dan
challenge_id; keberhasilan hanya dapat dikonsumsi sekali secara atomik.
Usulan rate limit: maksimal 5 pengiriman OTP per jam per email, ditambah pembatasan IP; setelah 10 kegagalan
login dalam 15 menit, terapkan cooldown 15 menit dengan jalur pemulihan yang tetap tersedia. Respons lupa
sandi tidak mengungkap apakah email terdaftar. Nilai final disahkan D1 agar tidak menyebabkan penguncian
akun oleh pihak lain.

3 Kebutuhan fungsional
Acceptance criteria menggunakan pola Diberikan, Ketika, Maka. Setiap aturan di bawah menjadi kontrak produk;
perubahan nilai berlabel Usulan ditangani melalui register keputusan. Pengujian negatif hak akses berlaku pada
seluruh fitur, bukan hanya pada layar admin.
3.1 Registrasi dan verifikasi email
F-01 | P0 | Cerita pengguna: Sebagai alumni baru, saya ingin membuat akun dan memverifikasi email agar
dapat melanjutkan pendaftaran keanggotaan.
Pendaftaran mengikuti stepper guidelines [R8]: Data Diri, OTP, Biaya KTA, Pembayaran. Langkah Data Diri
mengumpulkan nama lengkap, jenis kelamin, email, sandi, angkatan, kelas masuk dan kelas keluar (misalnya
Kelas 1 / 1 MTs sampai Kelas 6 / 3 Aliyah); tahun masuk, tahun keluar dan tahun lulus dihitung otomatis dari
angkatan dan kelas sesuai aturan pada 3.5 (disahkan v3.4). Email dinormalisasi sebelum pemeriksaan unik.
Akun baru berstatus pending_otp. Persetujuan privasi dan ketentuan dicatat beserta versi serta waktunya. Nomor
KTP/NIK tidak diminta; field Nomor KTP pada mockup guidelines tidak dipakai (disahkan v3.3).
AC F01-1: Diberikan email baru dan sandi valid, ketika registrasi dikirim, maka hanya satu akun pending_otp
dibuat dan challenge OTP diproses tanpa menampilkan kode ke klien.
AC F01-2: Diberikan OTP belum kedaluwarsa, ketika kode benar dikirim, maka akun menjadi active,
email_verified_at terisi, nomor anggota dialokasikan dengan KTA berstatus Tidak Aktif, dan pengguna
melanjutkan ke langkah Biaya KTA.
AC F01-3: Diberikan kode salah 5 kali, kedaluwarsa, pernah dipakai, atau diganti oleh resend, ketika
verifikasi dicoba, maka akses ditolak dan UI menawarkan alur challenge baru yang memenuhi cooldown.
AC F01-4: Diberikan request ganda atau jaringan putus, ketika klien mengulang registrasi, maka tidak ada
akun duplikat dan pengguna dapat melanjutkan verifikasi akun yang sama.
3.2 Login, pemulihan dan sesi
F-02 | P0 | Cerita pengguna: Sebagai pengguna, saya ingin login dan memulihkan akun tanpa kehilangan
kendali atas sesi perangkat.
Alumni masuk dengan email/sandi. Admin harus menyelesaikan TOTP sebelum memperoleh akses admin; sesi
tahap sandi tidak boleh memakai API admin. Backup code sekali pakai tersedia untuk pemulihan MFA. JWT
memuat identitas sesi, audience dan expiry; server memeriksa status/revocation untuk tindakan terlindungi.
AC F02-1: Diberikan login alumni valid, ketika token diterbitkan, maka access token berlaku 15 menit dan
profil effective_status menentukan rute serta izin.
AC F02-2: Diberikan admin yang belum membuktikan TOTP, ketika endpoint admin dipanggil, maka ditolak
walaupun sandi benar; tidak ada masa transisi aal1 di production.
AC F02-3: Diberikan refresh token yang sudah dipakai, ketika dipakai kembali, maka keluarga sesi dicabut
dan pengguna diminta login ulang; pergantian token dijalankan atomik.
AC F02-4: Diberikan pemulihan OTP valid, ketika sandi baru disimpan, maka seluruh sesi dicabut dan OTP
dikonsumsi; ganti sandi normal juga mensyaratkan sandi lama.
AC F02-5: Diberikan admin idle 30 menit, ketika request berikutnya dilakukan, maka sesi admin tidak lagi
berlaku. Peringatan UI muncul 2 menit sebelumnya; background polling tidak memperpanjang aktivitas.
AC F02-6: Diberikan pengguna memilih keluar semua perangkat, ketika operasi berhasil, maka HTTP dan
socket lama tidak dapat mengakses fitur terlindungi.

5 Arsitektur dan operasi
5.1 Batas sistem
Flutter, web admin dan situs publik hanya memakai API melalui Traefik dengan HTTPS/WSS. API NestJS
mengatur auth, membership, payments, content, events, network, chat, notifications, admin, files dan account.
PostgreSQL menyimpan state durable; Redis menyimpan antrean BullMQ, rate limit dan adapter realtime. Worker
memproses email/push, pengingat, expiry, ekspor, cleanup dan penghapusan akun.
Gambar 2 Arsitektur layanan
Outbox disimpan bersama perubahan bisnis di PostgreSQL. Dispatcher meneruskan ke BullMQ dengan dedup
key. Jika Redis/job hilang atau dispatcher mati setelah commit, outbox tetap dapat diproses ulang. Redis bukan
satu-satunya catatan keputusan atau notifikasi. Worker memakai least privilege dan lock/idempotensi per domain;
hasil antrean tidak boleh menggandakan uang, periode, nomor, kursi atau notifikasi.
5.2 Kontrak API dan realtime
API memakai prefix /api/v1, validasi skema server, pagination serta error baku berupa code, message,
field_errors dan request_id. OpenAPI 3.1 menghasilkan SDK Dart/TypeScript; skema bersama di TypeScript
bukan pengganti kontrak Dart. Socket memiliki versi event, event_id, entity_id, timestamp dan payload minimum.
Event dikirim sesudah commit dan bukan sumber kebenaran tunggal.

5.3 Topologi lingkungan dan kapasitas
Dev menggunakan Docker Compose lokal. Staging dan production memiliki database, user DB, Redis
namespace atau instance, volume berkas, secrets, domain dan proyek push yang terpisah. Jika memakai VPS
yang sama, keduanya tetap berbagi failure domain; staging tidak boleh melakukan stress test yang mengganggu
production. Data staging memakai data sintetis; data pribadi nyata tidak disalin ke staging.
VPS awal 4 vCPU, RAM 8 GB dan disk 100 GB di region Jakarta atau Singapura (disahkan v3.5); angka ini
adalah titik awal, bukan kapasitas yang dijamin. Beban Coolify, PostgreSQL, Redis, API, worker, build dan
monitor harus diukur pada Tahap 0. Usulan build image dijalankan CI agar kompilasi tidak menghabiskan RAM
production. D7 menyetujui kapasitas berdasarkan N-01 sampai N-06.
Firewall membuka 80/443; SSH 22 dibatasi IP tepercaya/VPN dan memakai key. PostgreSQL serta Redis tidak
diekspos publik. Coolify menggunakan subdomain terpisah, 2FA dan akses pengelola yang tercatat. Secrets
berada di pengelola secrets/Coolify dan GitHub Secrets, tidak masuk source, image layer, log atau frontend.
