# KAPDH Apps R1.0: acceptance traceability

Phase D, lens D2, updated at the final R1.0 integration (Phase D hardening of admin and mobile, Phase E E1-E4 merged;
`docs/handoff/integration-final.md`). This document maps every acceptance criterion in PRD v3.5 section 3 (AC F01-1
to AC F17-4, 87 criteria) and every non-functional target N-01 to N-16 (PRD 2.4) to the automated tests that prove
it. It also maps the UAT groups U-01 to U-13 (PRD 9.1) and the critical scenarios (PRD 9.2). `docs/BUILD_PLAN.md`
("Acceptance evidence") names this file as the release traceability record.

Final integration update. Rows whose status changed since the Phase D audit say so in their Notes/Gap column
("Final integration: ..."). Evidence added by the Phase D hardening (API, admin, mobile) and Phase E (E1 containers,
release job and go-live gate; E2 CI/CD and contract gate; E3 backup, restore, monitoring and load tooling) is cited
where it changes a status. Items that can only be proven on real staging/VPS infrastructure, GitHub Actions or
physical devices stay `partial` or `missing`; they are listed in section 6 and in `integration-final.md`.

ADR-025 update (15 October 2026). The product owner decided that step-up re-authentication (password + TOTP,
`X-Reauth-Token`) is required only for credential actions. These are resending an admin invitation, admin recovery,
correcting an admin's login email (conditional on `PATCH /admin/admins/{adminId}`), regenerating backup codes, member
password reset and member account deletion. Settings, payment-method and other admin create/update/delete operations
no longer ask for it (`docs/adr/025-reautentikasi-hanya-tindakan-kredensial.md`).
AC F15-3 and AC F16-1 are therefore marked **deviation**: their re-auth clause is deliberately not met, and every
other clause stays covered. Their evidence was re-cut. Citations marked `[pending]` come from test suites that
changed with ADR-025 and have not yet run in a verification run recorded in section 2. The next full run (including
the citation check) replaces them with its result. UAT items 1.16 and 10.3 in `uat-checklist.md` were updated
accordingly, and item 10.10 checks that the credential actions still ask for re-auth.

ADR-026 update (15 October 2026). At the product owner's request, payment methods gained the kind `qris`: the
organization's static QRIS, with a public QR image (`payment_qr`) uploaded through `POST /admin/payment-qr-images`
(`docs/adr/026-metode-qris-dan-gambar-qr-publik.md`). This adds to PRD 6.2 ("Bank/ewallet") and introduces no new AC,
so the totals below are unchanged. It extends the snapshot clause of AC F15-3: the QR image is part of the method
identity, it is copied into `payments.method_snapshot`, and it cannot be replaced once the method is `in_use`. The
evidence is cited in the AC F15-3 row and marked `[pending]` until the next recorded run. The other AC rows are
unchanged. UAT items 2.17-2.21, 5.13, 10.11-10.16, 12.10 and 13.10-13.11 cover QRIS manually.

## How this was built

1. Every test file in `kapdh-platform/apps/**`, `kapdh-platform/packages/**` and `kapdh-mobile/test/**` was scanned
   for AC ids (`F01-1` ... `F17-4`) and N ids (`N-01` ... `N-16`). Each hit was attributed to the enclosing `it` /
   `test` / `testWidgets` / `describe` / `group` call. Only hits in a test **name** count as evidence; ids that appear
   only in comments are ignored.
2. For every AC, the tagged test names were compared with each clause of the AC text. Test bodies were then read
   wherever a clause could plausibly be missing:
   - F01-1..F01-4, F02-2, F02-5 (`auth.e2e`, `otp.e2e`, `auth-otp.pg`);
   - F04-1..F04-5 (`admin-payments.e2e`, `payments-module.pg`);
   - F05-1, F05-6, F06-2 (`card-verify.e2e`);
   - F09-1 and the same-member race (`events-module.pg`);
   - F10-5 (`directory.e2e`, `me-profile.e2e`) and F12-1 (`chat-rooms.e2e`);
   - F14-3, F14-5, F14-6 (`deletion-job.e2e`, `expect-deleted.ts`);
   - F16-3 socket clause (`core/realtime.e2e`, realtime gateway);
   - the UI clauses of F05-2/F05-3 (`kta_screen_test`), F02-5 and F15-4 (admin).

   A clause without a direct assertion makes the status `partial`, and the gap is listed in section 6. For the
   remaining ACs the status rests on test names that state the clause explicitly, plus spot checks.
3. Every test suite that contains cited evidence was run on this tree (section 2). The generator then matched each
   cited test name to the run results. `[pass]` next to a test means that the test ran in this audit and passed.
4. The Evidence column lists up to three API tests and up to two tests for each other layer (the
   strongest ones by rank). "(+n more)" counts further tests that are tagged with the same id. To list every tagged
   test, search the repository for the id, for example `rg "F09-1"`.

Status legend:

- **covered**: every clause of the AC is asserted by at least one passing automated test.
- **partial**: some clauses are asserted, and at least one clause is not (see Notes / section 6).
- **missing**: no automated evidence.
- **deviation**: a clause is deliberately not met by a recorded product-owner decision (ADR). Every other clause is
  covered, and the Notes column points to the ADR.

Result markers: `[pass]` = ran and passed in the run of section 2; `[pending]` = cited after that run (ADR-025
change) and not yet run in a recorded verification run.

Layers: **API** = `apps/api` e2e/unit on PGlite (`pnpm --filter @kapdh/api test`); **API PG17** = real PostgreSQL
17 lane, role `kapdh_app`/`kapdh_worker` (`pnpm --filter @kapdh/api test:pg`); **Worker** = `apps/worker` (+ its PG
lane); **Packages** = `packages/{database,shared,config,storage}`; **Admin UI** = `apps/admin` (Vitest + Testing
Library against the dev:mock server); **Web** = `apps/web` (Vitest + jsdom); **Mobile** = `kapdh-mobile` Flutter
widget/unit tests (fake HTTP); **Contracts (Dart)** = generated SDK tests in `packages/contracts/dart/kapdh_api`.

## 8. Limits of this evidence

- Admin UI and web tests run against hand-written mock servers (`apps/admin/src/api/mocks/*`, `apps/web` fakes), and
  Flutter tests run against fake HTTP. They prove client behaviour for the contract shapes the mocks return. They do
  not prove that the merged API returns those shapes (finding D2-14). Since the Phase D hardening, every admin mock
  response is validated against the contract (`apps/admin/src/api/mocks/contract-conformance.test.ts`), and the admin
  live lane (`pnpm test:live`) proves the login/TOTP, session, idle warning and timeout, concurrent-decision and D13
  recording UI clauses against the merged API (PGlite, jsdom). Web and Flutter still have no run against the merged
  API.
- Fault and race evidence comes from injected failures and lock-forced races. Nothing here replaces the UAT on
  staging that PRD 9.3 requires. The PG17 lanes do run against a real PostgreSQL 17 with the production roles.
- The status is the auditor's judgement after reading the cited tests. It is not an automatic consequence of a test
  name containing the id.
