# Phase B handoff: contract C6-community

Contract author notes after build, adversarial review and fixes. The domain YAML files are the source of truth; this file explains decisions, open issues and implementation notes for the Phase C slice owners.

## fix summary
I checked all 9 review findings for C6-community. I fixed 8 of them in commit d49cde3, on top of bc82d88, and rejected 1. The full verification list passed after the fixes.

What was fixed:
1. **Invitation privacy.** room.member_changed with change invited, invitation_cancelled or declined now goes only to the user:<id> channels of the invitee and of each joined group admin, never to room:<room_id>. joined, left, removed and role_changed still go to room:<id> plus the affected user:<id>. An invitation cancelled because of a block, a group closing or an account deletion sends actor_user_id null, so a block cannot be told apart from those cases. The schema description, an added `invited` example, the README channel notes and the chat.yaml descriptions (createChatGroup, inviteChatMembers, declineChatInvitation, removeChatRoomMember, acceptChatInvitation, leaveChatRoom) and blockMember in moderation.yaml all say the same.
2. **Appeals.** I chose option (a): createAppeal is now limited to a suspension that is currently in force; anything else gets 403. Warnings cannot be appealed in R1.0. The server stores a snapshot of the appealed suspension in the new `AdminModerationEvidence.contested_suspension` field (schema AdminModerationContestedSuspension). An appeal can only be resolved with dismiss (rejected, outcome no_action) or unsuspend (granted, outcome action_taken). Any unsuspend, from a report decision or from the admin member menu, closes the member's open appeal as granted in the same transaction, so an appeal never stays open after its suspension is lifted.
3. **Conflict of interest in the admin queue.** adminListReports now leaves out any report whose reported party is the caller's linked alumni account. That covers items, total, counts and `q` search. For a group report with no subject, being a joined member of that group counts as being the reported party. adminGetReport, adminClaimReport and adminResolveReport now return 404 NOT_FOUND (previously 403) when the caller is the reported party. When the caller is the reporter, claim and resolve still return 403. resolve also returns 403 if subject_user_id is the caller's own linked account.
4. **Message order equals commit order.** Every insert into messages, including system messages, first locks the room row with SELECT ... FOR UPDATE. created_at is then set to greatest(clock_timestamp(), last_message_at + 1 µs), and last_message_at is updated in the same transaction. The client sync anchor comes only from HTTP history pages, because socket events can arrive out of order. After reconnect the client calls `?after=<anchor>` until next_cursor is null. This is documented in chat.yaml (domain rules, listChatMessages, sendChatMessage, ChatMessage.created_at), realtime-chat-message, message.created and events/README.md.
5. **POST /chat/direct.** It returns 403 only when the caller is the one who blocked. A block by the other person is treated like an unavailable peer: an existing room comes back as 200 with can_send false and send_restriction peer_unavailable, and with no room the response is 404, with the same code and message as an inactive peer. This matches getMemberProfile, which also returns 404 to a blocked caller. sendChatMessage and addChatReaction now state that the error message is the same for a block by the other person and for an unavailable peer.
6. **ChatRoomSummary.peer** is now in `required`, so it is always present: an object for direct rooms, null for groups.
7. **Offline deletions and reactions.** After reconnect, and every time a room is opened, the client reloads the message window it shows and replaces its local copies. Local copies are shown only until the HTTP page arrives, so deletions made while offline (including AC F14-3) always take effect. This is documented in listChatMessages, message.deleted and events/README.md.
8. **reports.due_at.** The CHANGELOG list of database dependencies now includes making due_at NOT NULL. The contract keeps due_at required and non-null, and the admin-moderation header says the server always sets it on insert. The CHANGELOG also has a new section listing these behaviour rules.
9. Rejected (see open_issues).

No operation was added or removed; there are still 83. The only shape changes are one new schema, one new required field (`contested_suspension`) and `peer` becoming required.

## second fix round (7 findings, all fixed)
1. **Room subscriptions end at expiry.** chat.yaml domain rules and events/README.md ("Pencabutan langganan room") now bind the gateway: only active joined members are put in room:<id>; the gateway schedules removal from every room channel at alumni.expires_at; it also revokes immediately when a chat HTTP call returns MEMBERSHIP_REQUIRED/ACCOUNT_SUSPENDED or a typing/presence.ping emit is refused; a sweep runs at least every 60 s; sockets are re-joined after renewal/unsuspend. The client learns of expiry from the 403 and from /me expires_at.
2. **Read limits match write limits.** NetworkMemberProfile.phone maxLength 24 (was 20); NetworkSocialLinks instagram/x/facebook maxLength 200 (was 120).
3. **Group avatar in evidence.** AdminModerationEvidenceRoom.avatar (AdminModerationEvidenceImage | null) is new and required; files referenced by evidence are kept until D2 retention removes them.
4. **Conflict-of-interest counts.** admin-moderation.yaml rule c) says every report count shown to admins (DashboardModeration.*, AdminNavBadges.reports_open, AdminMemberDetail.moderation for the caller's own linked account) must use the same visibility rule as adminListReports. The other domains still need the change (blocking, below).
5. **Appeals without the admin-members fix.** The admin-members unsuspend dependency is now stated as a blocking cross-domain dependency, not an assumption. Safety net inside C6: new AdminModerationContestedSuspension.in_force; a stale appeal (in_force false) can only be closed with unsuspend, which grants it without changing membership, and dismiss returns 400; createAppeal closes a stale active appeal as granted and creates a new one for the current suspension, under the alumni row lock.
6. **Chat push only for active members.** sendChatMessage schedules chat push only for joined members other than the sender who are verified/expiring and not suspended, have not muted the room, and have chat push enabled.
7. **Strict member-facing schemas.** Every response schema in chat.yaml and moderation.yaml has additionalProperties: false. ChatPeer, ChatRoomMember and ChatRoom no longer use allOf (parent fields repeated), so Dart drops `implements ChatUserRef/ChatRoomSummary`; JSON names are unchanged.

Blocking cross-domain changes (not made, other owners): admin-dashboard.yaml counts (C7), admin-members.yaml adminUnsuspendMember closing appeals via a shared MembershipKernel.unsuspend and AdminMemberDetail.moderation exclusion (C2), core/files retention of evidence files. Details are in packages/contracts/CHANGELOG.md, section "Ketergantungan lintas domain C6".

## contract/shared changes
- DB (packages/database, not made): add the value 'appeal' to the enum app.report_category. An appeal is a report with category appeal, target_type user and target_user_id = reporter_id (PRD 3.12).
- DB (not made): add these columns to app.reports: claimed_by_admin_id uuid (references admins.id ON DELETE SET NULL, partial index), claimed_at timestamptz, member_message text (at most 500), message_removed_at timestamptz. Optional CHECK: status <> 'in_review' or claimed_at is not null.
- DB (not made): ALTER app.reports.due_at SET NOT NULL. The contract requires due_at to be non-null; the server computes it on insert (24 h for urgent, 2 business days otherwise).
- admin-members domain (other author): every unsuspend path must, in the same transaction, close the member's open appeal (reports with category appeal and status open/in_review, target_user_id = member) as status resolved, action unsuspend, with a resolution_note referencing the unsuspend. It must also notify the appellant (account category, outcome action_taken).
- chat module implementer: every INSERT into messages (member and system messages, including account-deletion reassignment messages) must first take SELECT ... FOR UPDATE on the rooms row as the first lock in the transaction. It sets created_at explicitly to greatest(clock_timestamp(), rooms.last_message_at + interval '1 microsecond'), not the column default now(), and updates rooms.last_message_at in the same transaction.
- realtime/chat implementer: emit room.member_changed for invited, invitation_cancelled and declined only via emitToUser (the invitee plus each joined group admin), never emitToRoom. Cancellations caused by a block, a group closing or an account deletion use actor_user_id null.
- core-api / files (unchanged from the builder): GET /files/{id}/access for purpose chat_image must check that the caller is a joined member who can see the message (AC F11-4); signed URLs last at most 10 minutes.
- packages/contracts/scripts/lib/dart/fixture.mjs (contracts infra, changed by the builder in WIP commit 77529c2, not in this fix): the fixture forces 'typing' to pending and 'session.revoked' to payload-less, so both generator states stay tested. The contracts-infra owner should review it.
- packages/contracts/dart/kapdh_api/test/models_test.dart (hand-written test, rewritten by the builder): uses a valid sample payload for every event type. Not changed in this fix; the contracts-infra owner should review it.
- notifications domain: deep links for the chat category are kapdh://app/chat/invitations and kapdh://app/chat/<roomId>. Moderation and appeal outcomes go in the account category with deep link /account/reports. The notification.created payload mirrors InboxNotification.

## open issues
- rejected: finding 9 (the builder report had no shared_changes and did not mention fixture.mjs or the DB changes). Reason: the builder's report did have a shared_changes array listing fixture.mjs, models_test.dart and the DB enum and column additions. The only thing missing was reports.due_at NOT NULL, which is now in the CHANGELOG and in shared_changes above, along with the other shared edits, so their owners can see them.
- Product decision to confirm: in R1.0 only a suspension that is currently in force can be appealed (option (a) from the finding). Warnings cannot be appealed through the app; members object through the support contact. Supporting warning appeals would need new enum values (report_action, e.g. revoke_warning, and membership_event_kind, e.g. warn_revoked) and a resolve action that grants without changing membership.
- Conflict-of-interest scope for group reports with no subject: every joined member of the reported group is treated as a reported party and does not see the report. This is deliberately conservative. If a group's members include every admin with moderation permission, nobody can see the report until another admin is given access.
- The moderation contract still depends on the DB changes listed in shared_changes (report_category 'appeal', reports.claimed_by_admin_id, claimed_at, member_message, message_removed_at, due_at NOT NULL). They must land before the moderation module is built.
- The hand-written Dart test files (api_test, catalog_test, models_test) are not dart format-clean. No check enforces dart format.
